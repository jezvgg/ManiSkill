# Роботы Fetch в этом репозитории

`fetch_cam224`, `mikasa_ds_fetch` и `ds_fetch` — три разных UID. Таблица описывает конфигурации этой ветки при настройках по умолчанию и режиме **`pd_joint_delta_pos`**. Для других режимов смысл каналов нужно проверять отдельно.

| Свойство | `fetch_cam224` | `mikasa_ds_fetch` | `ds_fetch` в jezvgg/ManiSkill |
|---|---|---|---|
| Класс | `FetchOurCameras(Fetch)` | `MikasaDSFetch(Fetch)` | `DSFetch(Fetch)` |
| Назначение | Штатная модель Fetch с камерами 224×224 для RGB replay/политики | Робот оракулов MIKASA | Исходный робот задач форка jezvgg |
| URDF | `mani_skill/assets/robots/fetch/fetch.urdf` | `utils/mikasa/agents/ds_fetch/fetch.urdf` | `mani_skill/examples/motionplanning/fetch/fetch.urdf` |
| Камеры по умолчанию | `fetch_head`, `fetch_hand`, обе 224×224 | `fetch_head`, `fetch_hand`, обе 224×224 | Две вынесенные камеры `left/right_base_camera_link` 256×256 и `fetch_hand` 128×128; `fetch_head` отключена |
| Поле зрения | 2 рад у обеих камер | 2 рад у обеих; головная допускает override | 1.5 рад у вынесенных, 2 рад у кистевой |
| Действие | **13 чисел** | **13 чисел** | **14 чисел** |
| Рука | 7 нормированных приращений, ±0.1 рад за шаг | То же | То же |
| Захват | 1 нормированная абсолютная команда, отображаемая в −0.01…0.05 м | То же | То же |
| Голова и торс | 3 нормированных приращения: ±0.1 рад / ±0.1 м за шаг | То же | 3 абсолютных ненормированных положения; включена интерполяция |
| База | 2 канала: продольная скорость и поворот | 2 канала: продольная скорость и поворот | 3 канала: продольная и боковая скорости, поворот |
| Диапазон скорости базы | ±1 м/с; ±3.14 рад/с | То же | ±1 м/с по обеим осям; ±3.14 рад/с |
| Три roll-сустава руки | `continuous`, без позиционных границ в URDF | `revolute`, ±3.141 рад | `revolute`, ±3.141 рад |
| Поворот виртуальной базы | `continuous` | `revolute`, ±50 рад | `revolute`, ±6.28 рад |
| Система координат кисти | Штатная | Поворот `gripper_axis` примерно `(π, −π/2, 0)` и соответствующие меши | Такой же поворот кисти, как у MIKASA |
| Инерция кисти и пальцев | Штатные значения в штатных локальных осях | Центры масс и тензоры приведены к повёрнутым локальным осям | В повёрнутой системе оставлены старые численные значения инерции |

`fetch_cam224` меняет у класса `Fetch` только UID и размеры камер: URDF, контроллеры, крепления камер, поле зрения и прочие свойства наследуются. Числа поз кистевой камеры у него и MIKASA записаны в разных локальных осях кисти; сравнивать их напрямую без преобразования координат нельзя. Одинаковое разрешение не означает одинаковую динамику роботов.

В `mikasa_ds_fetch` уже есть отдельный GPU-hook, который передаёт обновлённые целевые положения в PhysX на каждом физическом подшаге. Его режим `pd_ee_delta_pose` также отличается: приращения задаются относительно мобильной базы, по умолчанию с масштабами 0.2 м и 0.5 рад. Это отдельный режим, его параметры не описывают joint-delta действия из таблицы. Эти возможности были в принятой базе PR №7; текущий пакет обновляет камеры и URDF этого робота.

По сравнению с `dair` после PR №7 у `mikasa_ds_fetch` меняются камеры (на две 224×224), пределы roll-суставов (±6.28 → ±3.141) и инерция кисти/пальцев. UID `ds_fetch`, его класс и URDF не изменяются. Предел поворота базы MIKASA ±50 уже был в `dair`.

## Откуда берётся путаница с ds_fetch

В исходном проекте MIKASA собственный робот называется `ds_fetch`. При публикации экспортёр переименовывает его в **`mikasa_ds_fetch`**, чтобы не заменить уже существующий `ds_fetch` в форке jezvgg. Поэтому запись «на ds_fetch» требует указания репозитория и версии. В этом публичном репозитории менять `robot_uids="mikasa_ds_fetch"` на `"ds_fetch"` без преобразования управления нельзя: отличаются и размер действия, и его смысл, и камеры.

## Запись, обучение и оценка

Инструкция исходной ветки `mikasa/tasks-vla` для `retrieval-try-1` описывает такую цепочку: оракул исполняет действия на MIKASA-роботе в режиме state; те же действия повторяются на `fetch_cam224`, откуда записываются RGB, qpos и успешность; обучение openpi читает сохранённые данные. Во время обновления весов отдельный робот не запускается.

Оценщик в том экспорте жёстко выбирает `mikasa_ds_fetch`. Следовательно, обучение по кадрам `fetch_cam224` и оценка на MIKASA-роботе используют разные физические модели. Успешный replay фиксированных действий подтверждает их исполнимость, но не устанавливает качество обученной политики при такой смене робота. Для сравнения нужен один checkpoint, одинаковые seed, частота и обработка наблюдений на обоих роботах. Эти эксперименты не являются результатами данного PR.

## Проверки UID внутри RoboCasa

Наследование класса `Fetch` не делает новый UID полностью прозрачным для среды:

- `RoboCasaSceneBuilder` отдельно проверяет `robot_uids == "fetch"` при настройке коллизий и начального состояния.
- Таблица отступов `ROBOT_FRONT_FACING_SIZE` содержит `fetch: 0.8`; MIKASA регистрирует `mikasa_ds_fetch: 0.8`. Для `fetch_cam224` и публичного `ds_fetch` остаётся fallback 0.7 м.
- Задачи MIKASA содержат собственные восстановление позы и настройку коллизий для нестандартного UID. Списки `SUPPORTED_ROBOTS` выбранных задач пока объявляют `mikasa_ds_fetch` и `fetch`.

Поэтому `fetch_cam224` здесь — зарегистрированный класс со штатной моделью робота; идентичность полной сцены со случаем `fetch` и поддержка всех задач на этом UID не заявляются. Оракулы выбранных задач используют `mikasa_ds_fetch`.

## Выбранные задачи

Этот пакет обновляет `MikasaCabinetSearch-v0` и добавляет `MikasaWaterPlants-v0` и `MikasaDepthRecall-v1`. В DepthRecall-v1 по умолчанию четыре объекта и семь переносов: четыре извлечения, три возврата. Общие функции укладки на полку находятся в `utils/mikasa_oracle/planners/cabinet_place.py`; отдельная задача CabinetStow для них не требуется.

Для проверки оракулов в Linux-окружении с RoboCasa, mplib и рабочим рендерером:

```bash
uv run python -m utils.mikasa_oracle.evaluate_planner -s MikasaCabinetSearch-v0 -p cabinet_search_planner -n 2 --start-seed 9000 --scene-idx 0 --obs-mode state --control-mode pd_joint_delta_pos
uv run python -m utils.mikasa_oracle.evaluate_planner -s MikasaWaterPlants-v0 -p water_plants_planner -n 2 --start-seed 9000 --scene-idx 0 --obs-mode state --control-mode pd_joint_delta_pos
uv run python -m utils.mikasa_oracle.evaluate_planner -s MikasaDepthRecall-v1 -p depth_recall_v1_planner -n 2 --start-seed 9000 --scene-idx 0 --obs-mode state --control-mode pd_joint_delta_pos
```

Это команды для проверки, а не утверждение об успешных физических прогонах. Для исследования качества нужны отдельные согласованные наборы seed и полная статистика.
